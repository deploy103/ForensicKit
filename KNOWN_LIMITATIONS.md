# Known Limitations

- Native Registry analysis intentionally does not replay transaction logs or fully enumerate untrusted hive trees. It treats transaction-log recovery as a separate, reproducible verification step.
- Native EVTX analysis frames records and preserves their IDs, timestamps, sizes, and byte offsets but does not decode BinXML. Structured Chainsaw JSON/JSONL records are boundedly normalized and joined to native offsets only by exact EventRecordID; unmatched records remain uncorrelated and raw tool output remains authoritative.
- Native USN journal parsing is activated only for an artifact named as the `$UsnJrnl:$J` stream, scans the first/last 8 MiB, and supports aligned USN_RECORD_V2/V3/V4 structures. V3/V4 128-bit identifiers remain opaque exact values; V4 exposes bounded range extents but has no filename/timestamp fields. It does not infer full paths or imply that a reason mask proves user intent.
- Windows event activity clusters ignore timestamps without an explicit UTC marker or numeric offset. Scores are capped, fully explained prioritization leads based on nearby known Event IDs; they are not behavioral verdicts and do not replace surrounding-event review.
- Minidump metadata parsing is not a replacement for Volatility or a debugger; CPU contexts and process-memory object pointers are not dereferenced.
- iOS directory bundle ingestion preserves members as independent roots. It correlates only exact `Manifest.db` file IDs; it does not infer absent payload paths, decode opaque metadata BLOBs, or duplicate an immutable root as a child artifact.
- The base development environment lacks pytest and an installed Textual package, so direct synthetic tests remain the default fallback. The case viewer was additionally validated headlessly against an isolated Textual 8.2.8 installation; the competition image must still carry the staged offline UI/test wheels.
- Tool availability depends on the local workstation. Missing optional executables are planned/reported safely but not run.
- Offline bundles must be built on a matching Debian-family distro release and architecture; the scripts intentionally do not promise cross-distro package compatibility.
- Native NTFS parsing validates record zero and samples at most 256 MFT records (at most 1 MiB of mapped reads) through its validated unnamed `$DATA` run list. It reads at most 64/1 MiB of nonresident `$I30` only when each mapped INDX buffer and USA fixup validate. Unused INDX allocation bytes receive a strict aligned plausibility scan, but resulting slack records are lower-confidence stale/deleted candidates rather than active membership. It recovers bounds-validated resident streams and complete nonresident streams only when runs are uncompressed, unencrypted, contiguous in logical VCN space, and every allocated range maps inside the image. `$ATTRIBUTE_LIST` extents are joined only when all required records fall inside the sample and exact target/base sequences, attribute IDs/names, flags, and VCNs agree. Sparse ranges and bytes from initialized size through real size are explicit logical zero fill; incomplete/out-of-sample extent sets remain unrecovered. Use SleuthKit for exhaustive recovery.
- `$MFTMirr` comparison currently covers only record zero, requires each complete record to be at most 4 KiB, and does not automatically replace or repair a damaged primary MFT. Divergence is a consistency lead, not proof of tampering.
- NTFS backup-boot comparison treats the final evidence sector as the backup location and requires a valid NTFS signature/end marker before comparison. It is intended for a volume/partition artifact beginning at NTFS sector zero; a larger whole-disk container still requires partition-offset-aware verification.
- Native FAT32 analysis traverses the root and active subdirectories under 32-directory/64-cluster/8-MiB bounds, but never follows deleted directory entries. Root LFNs require bounded checksum/UTF-16 validation. It recovers bounded nonempty regular files through one mapped cluster or a complete chain ending exactly at EOC while warning that deleted clusters may have been reused. FAT12 remains unsupported; FAT16's narrower fixed-root coverage is described below.
- Native FAT16 analysis validates the BPB-derived cluster-count class, FAT capacity, and fixed-root geometry before scanning at most 4,096 entries. It follows only active subdirectories whose complete chains reach EOC under shared 32-directory/64-cluster/8-MiB bounds; incomplete or shared chains do not supply deleted children. Deleted LFN chains require the same checksum/UTF-16/order safeguards as FAT32. It recovers bounded nonempty root/subdirectory regular files directly when one cluster suffices or through at most 64 current FAT entries ending exactly at EOC, always retaining the deleted-cluster reuse caveat. FAT12 remains unsupported; use SleuthKit for exhaustive recovery.
- Native ext analysis traverses at most 32 allocated active directories under shared 64-block/8-MiB bounds through complete initialized ext4 depth-zero, depth-one, or depth-two extent trees, or ext2/3 direct plus one single-indirect pointer block. Inode, directory-data, extent-tree, indirect-metadata, and data-block reuse is boundedly rejected, and exact intermediate-index/leaf/pointer/data offsets are retained. It recovers at most 128 allocated nonempty regular files from validated root/subdirectory entries when their initialized mapping is complete under 8-MiB/64-block per-file bounds. It does not follow double/triple-indirect blocks or depth-three-and-higher extent trees, journal state, metadata checksums, sparse files, or deleted entries; use fsck/SleuthKit against a copy for exhaustive work.
- Native exFAT analysis independently validates complete main/backup boot regions and compares immutable bytes without choosing an authoritative divergent copy. It traverses the root plus at most 32 active subdirectories under shared 64-cluster/8-MiB bounds, supporting complete NoFatChain extents and exact-EOC FAT chains while rejecting shared clusters and never traversing deleted directories. It validates bounded active allocation-bitmap/upcase metadata; inactive sets require a restored-InUse checksum and name hashes are revalidated only with a trusted full upcase mapping. Root/subdirectory deleted regular files receive initialized-tail zero fill and current bitmap reuse warnings without ownership verdicts. Exhaustive directory enumeration and recovery still require SleuthKit.
- Native TLS certificate inventory reassembles only one bounded (64 KiB) TLS 1.2/1.3 Certificate record per in-order TCP flow and records opaque certificate lengths/fingerprints. It does not decrypt TLS, join multiple TLS records/handshakes, or interpret X.509 subject/issuer/extensions; use tshark or local X.509 tooling for that verification.
- Native HTTP recovery handles complete length-delimited or chunked HTTP/1.x responses, exact inverse-flow request pairing, bounded gzip/deflate content coding, and strictly delimited multipart response parts including Base64 and quoted-printable Content-Transfer-Encoding. It does not support brotli/zstd coding, HTTP/2/3 framing, nested MIME transfer encodings, or arbitrary TCP streams; use tshark for exhaustive protocol reconstruction.
- Native FTP recovery currently accepts observed IPv4 PASV/EPSV or active-mode PORT/EPRT `RETR` downloads and `STOR` uploads after an exact control-channel correlation, including bounded in-order control-line continuation. PASV/EPSV and active-mode `MLSD`/`NLST` listings are preserved as child artifacts, with command-specific `226`/4xx/5xx completion/error provenance. It records exact `AUTH TLS`/`234` provenance and discards later plaintext/stale transfer state, but does not decrypt TLS-protected FTP; use tshark for exhaustive protocol reconstruction.
- Native SMTP recovery accepts bounded retransmission-safe TCP reassembly of DATA/354 control exchanges and DATA body bytes ending in the SMTP dot terminator. It extracts declared flat and `message/rfc822` MIME attachments plus inline Content-ID objects through the standard-library parser, including bounded RFC 2231/5987 decoded names, scans top-level multipart/alternative text parts with MIME provenance, and correlates exact final 250, 251/252 forwarding, and 4xx/5xx replies. It records STARTTLS transitions and suppresses native plaintext parsing after the exact 220 handshake, and recovers complete declared-length BDAT messages with the same bounded MIME attachment handling and final-response provenance. No TLS decryption is attempted.
- Native POP3 recovery accepts only exact TCP/110 `RETR <message-number>` / inverse `+OK` exchanges, then reassembles one bounded dot-terminated multiline response with retransmission-safe packet provenance. Recovered messages receive bounded standard-library MIME attachment handling. It records exact `STLS`/`+OK` provenance and suppresses later plaintext recovery, but does not decrypt TLS or support implicit TLS, UIDL/LIST/TOP, or arbitrary pipelining beyond ordered RETR replies; use tshark for exhaustive protocol reconstruction.
- Native IMAP recovery accepts only full-message `FETCH` requests on TCP/143 whose inverse response supplies one exact `BODY[]`/`RFC822` literal and whose original tag receives a final `OK`. Recovered messages receive bounded standard-library MIME attachment handling. It records exact tagged `STARTTLS`/`OK` transition provenance and suppresses later plaintext recovery, but does not decrypt TLS or support IMAPS, authentication, arbitrary FETCH item syntax, multiple literals, non-message body sections, or general IMAP state reconstruction; use tshark for exhaustive protocol reconstruction.
- Native SMB2 analysis inventories complete bounded TCP/445 Direct TCP NEGOTIATE/TREE_CONNECT/CREATE/CLOSE and SET_INFO rename/delete-disposition exchanges with exact inverse response provenance, retaining dialect/signing/capability/transport limits, validated UNC share paths, relative/target filenames, NTSTATUS, success FileIds, final sizes, attributes, and raw GUID/FILETIME values. It reconstructs only acknowledged WRITE requests or successful READ responses that form a conflict-free stream from offset zero, enforces final EndOfFile when a successful CLOSE is captured, and promotes strictly bounded FileNamesInformation or FileIdBothDirectoryInformation QUERY_DIRECTORY responses as text/JSONL children. NEGOTIATE contexts are bounds-checked but not decoded; SMB3 encryption/compression transform headers are inventoried but their payloads remain opaque. Native support does not parse other directory-information classes, retain partial/gapped transfers as children, apply captured mutations, decrypt SMB3, decompress transforms, or support SMB1; use tshark for exhaustive protocol reconstruction.
- Native PCAP extraction summaries are protocol-scoped; a non-HTTP child never serves as evidence for an HTTP-object finding.
