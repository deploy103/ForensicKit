# Known Limitations

- Native Registry analysis intentionally does not replay transaction logs or fully enumerate untrusted hive trees. It treats transaction-log recovery as a separate, reproducible verification step.
- Native EVTX analysis frames records and preserves their IDs, timestamps, sizes, and byte offsets but does not decode BinXML. Structured Chainsaw JSON/JSONL records are boundedly normalized and joined to native offsets only by exact EventRecordID; unmatched records remain uncorrelated and raw tool output remains authoritative.
- Native USN journal parsing is activated only for an artifact named as the `$UsnJrnl:$J` stream, scans the first/last 8 MiB, and supports aligned USN_RECORD_V2/V3/V4 structures. V3/V4 128-bit identifiers remain opaque exact values; V4 exposes bounded range extents but has no filename/timestamp fields. It does not infer full paths or imply that a reason mask proves user intent.
- Windows event activity clusters ignore timestamps without an explicit UTC marker or numeric offset. Scores are capped, fully explained prioritization leads based on nearby known Event IDs; they are not behavioral verdicts and do not replace surrounding-event review.
- Minidump metadata parsing is not a replacement for Volatility or a debugger; CPU contexts and process-memory object pointers are not dereferenced.
- iOS directory bundle ingestion preserves members as independent roots. It correlates only exact `Manifest.db` file IDs; it does not infer absent payload paths, decode opaque metadata BLOBs, or duplicate an immutable root as a child artifact.
- The base development environment lacks pytest and an installed Textual package, so direct synthetic tests remain the default fallback. The case viewer was additionally validated headlessly against an isolated Textual 8.2.8 installation; the competition image must still carry the staged offline UI/test wheels.
- Tool availability depends on the local workstation. Missing optional executables are planned/reported safely but not run.
- Native CPIO parsing currently supports portable ASCII `odc` (`070707`) and SVR4 `newc`/CRC (`070701`/`070702`) archives from offset zero. It inventories at most 4,096 entries under the configured artifact count and signature-scan byte bounds, keeps odc octal/76-byte/two-byte-alignment semantics separate from newc hexadecimal/110-byte/four-byte alignment, verifies at most 16 MiB of CRC member data during triage, and copies only exact-range regular files under the ordinary recursion/count/byte budgets. Symlinks, hard-link semantics, devices, FIFOs, sockets, absolute/drive-rooted paths, and parent traversal are never materialized; CRC verdicts are byte-sum integrity evidence, not authenticity. Binary CPIO, concatenated archives, and recovery after a malformed header are not yet supported.
- Native ISO 9660 parsing validates at most 64 2-KiB volume descriptors. Each selected primary or highest-level valid Joliet namespace reads its root plus at most 32 unique active subdirectories under an independent 8-MiB/4,096-entry bound. It checks both-endian fields, declared/evidence ranges, block-bounded record framing, extent locations, component-safe identifiers, timestamps, `.`/`..` consistency, and rejects cycles, shared extents, and unsupported layouts. Primary and active-Joliet mandatory and present optional path-table copies are independently bounded to 8 MiB/4,096 entries, hashed, semantically compared across byte orders, and reconciled to their sampled directory records without becoming authoritative. Joliet `%/@`/`%/C`/`%/E` names and path tables use strict big-endian UCS-2 (no surrogates); exact unique byte ranges or ordered multi-extent range sequences reconcile names without duplicate extraction, but this is an alias, not proof the two directory hierarchies are semantically identical. SUSP is activated only by a valid root-self `SP`; inline and `CE`-continued RRIP entries retain raw/absolute/source provenance. CE traversal is bounded to 1 MiB/128 areas/depth 8, hashes each area, and rejects overlaps/cycles; only fully resolved complete safe UTF-8 `NM` chains drive paths. PX/SL symlinks or special files are never materialized. Valid regular-file `PX` serial/link-count claims are grouped only when exact extent sequences agree; one payload may be copied once while aliases remain metadata, incomplete groups stay partial, contradictory groups are not reconciled, and no host hard links are created. `TF` short/long times preserve raw/local-offset/UTC evidence, and both-endian `PN` device numbers remain metadata-only. `CL`/`PL`/`RE` links are role-checked and reconciled to known directory extents but deliberately never traversed, so relocated directory contents require external verification; non-UTF-8 locale name interpretation remains unresolved. El Torito support validates up to eight boot-record/catalog pairs, reads at most 8 KiB/64 section slots per catalog, validates section/extension framing, and can copy deterministic default/section no-emulation or fixed-floppy load ranges. Hard-disk-emulation entries receive one exact MBR-sector read with partition/range/overlap checks, but the last partition end is only a minimum covered length and not a full image boundary, so those entries remain metadata-only. Other boot children represent only declared initial load bytes, not necessarily complete boot filesystems; platform/vendor selection semantics remain metadata-only. Safe regular files may become children from one complete non-interleaved extent or at most 128 adjacent identifier/version/volume-consistent records whose non-final lengths are block-aligned and whose ordered non-overlapping ranges total no more than the configured single-artifact limit. Every segment record and any zero block padding are revalidated during copying; incomplete, inconsistent, or over-limit chains are wholly suppressed. Interleaving, UDF, zisofs compression, and deleted/slack records remain unsupported; use 7z/SleuthKit-compatible tooling for exhaustive analysis.
- Offline bundles must be built on a matching Debian-family distro release and architecture; the scripts intentionally do not promise cross-distro package compatibility.
- Native NTFS parsing validates record zero and samples at most 256 MFT records (at most 1 MiB of mapped reads) through its validated unnamed `$DATA` run list. It reads at most 64/1 MiB of nonresident `$I30` only when each mapped INDX buffer and USA fixup validate. Unused INDX allocation bytes receive a strict aligned plausibility scan, but resulting slack records are lower-confidence stale/deleted candidates rather than active membership. It recovers bounds-validated resident streams and complete nonresident streams only when runs are uncompressed, unencrypted, contiguous in logical VCN space, and every allocated range maps inside the image. `$ATTRIBUTE_LIST` extents are joined only when all required records fall inside the sample and exact target/base sequences, attribute IDs/names, flags, and VCNs agree. Sparse ranges and bytes from initialized size through real size are explicit logical zero fill; incomplete/out-of-sample extent sets remain unrecovered. Use SleuthKit for exhaustive recovery.
- `$MFTMirr` comparison currently covers only record zero, requires each complete record to be at most 4 KiB, and does not automatically replace or repair a damaged primary MFT. Divergence is a consistency lead, not proof of tampering.
- NTFS backup-boot comparison treats the final evidence sector as the backup location and requires a valid NTFS signature/end marker before comparison. It is intended for a volume/partition artifact beginning at NTFS sector zero; a larger whole-disk container still requires partition-offset-aware verification.
- Whole-disk filesystem boot validation reads one 512-byte sector at each of the four primary MBR starts, at most 32 EBR-derived logical starts, or at most 32 entries from a structurally and CRC-valid primary GPT. EBR walks retain current-EBR versus extended-base-relative semantics and stop on invalid markers/links, bounds, cycles, or the shared limit. FAT, NTFS, and exFAT candidates receive format-specific checks plus independent table-type/start/length comparison. Structurally valid data entries across those bounded primary/logical/GPT inventories are compared for exact duplicate, containment, or partial-overlap ownership; extended and protective MBR container entries are excluded from that conflict verdict. A complete partition may be copied—not mounted—as a recursive child only when its table entry and boot structure validate, its full extent is present, no competing data entry claims any of its sectors, and ordinary depth/count/single/cumulative byte limits allow it; ambiguous, larger, or partial partitions remain observation-only. The GPT backup header and its complete bounded entry table are independently CRC/geometry/content checked, but a damaged backup does not override a valid primary. Non-512-byte logical partition addressing and exhaustive large-partition traversal still require SleuthKit.
- Native FAT recognition without a textual type label requires a complete 512-byte volume boot sector whose jump, marker, geometry, mutually exclusive fields, variant layout, cluster-count class, and FAT entry capacity all validate. When present, the informational label and BPB-derived class are retained independently and the validated cluster-count class drives bounded parsing. The validator does not yet infer a partition offset, repair inconsistent fields, or treat a supplied image shorter than the BPB-declared volume as structural invalidity. Malformed-BPB findings are review leads and do not by themselves suppress independently bounded native parsing selected from an otherwise explicit label.
- Native FAT32 analysis validates an FSInfo sector and the conventional backup FSInfo location only when both BPB sector references stay inside the reserved region and FAT capacity covers the BPB-derived FAT32 cluster count. Free-count/next-free fields are hints, not allocation truth, and divergent valid copies are not automatically reconciled. All declared FAT ranges are independently bounded and compared for at most 8 MiB. Each available copy's first two reserved entries is checked against the BPB media descriptor and reserved/EOC patterns; the upper reserved nibble and clean-shutdown/hard-error flags are preserved rather than rewritten. Mirrored copies must compare completely and equally; with mirroring disabled, the BPB ExtFlags-selected table drives all native chain traversal and inactive-copy divergence alone is not called corruption. Reserved ExtFlags, invalid/unavailable active indices, unavailable copies, malformed reserved entries, and incomplete mirrored comparisons remain anomalies. It traverses the root and active subdirectories under 32-directory/64-cluster/8-MiB bounds, but never follows deleted directory entries. Active and deleted directory cluster fields are masked to 28 bits; nonzero reserved high nibbles remain visible anomaly metadata but are excluded from native content recovery. Named active files require exact size-required EOC chains. Active LFN failures and end-marker-orphaned slots in roots/subdirectories, plus subdirectory volume-label incompatibilities, retain exact slot provenance and never supply a trusted long name. Bounded validated directory identities are ordered per level but are not rendered as an inferred full path. Deleted subdirectory LFNs require the same unique missing-short-byte checksum solution, physical-order, UTF-16, and padding validation as root LFNs; deleted-file recovery still warns that clusters may have been reused. The active FAT is scanned for at most 131,072 data-cluster entries; chain components not reached from the bounded active-directory start set retain exact FAT/data offsets, but remain ownership-free lost-chain leads. At most 32 complete EOC candidates totaling 8 MiB can be materialized for recursion; the whole last cluster is kept because logical size is unknown, so it may include slack. Narrower FAT12/16 coverage is described below.
- Native FAT16 analysis validates the BPB-derived cluster-count class, FAT capacity, and fixed-root geometry before scanning at most 4,096 entries. Every BPB-declared FAT copy is independently image/volume-bounded and compared with copy zero for at most 8 MiB; an oversized table can therefore retain a prefix result without claiming a complete match, and no copy is selected as authoritative. Its reserved entries are independently checked against the BPB media byte and reserved/EOC pattern while retaining dirty/I/O-error status bits as state, not invalidity. It follows only active subdirectories whose complete chains reach EOC under shared 32-directory/64-cluster/8-MiB bounds; incomplete or shared chains do not supply deleted children. Active directory/file and deleted-file LFNs require checksum/UTF-16/order safeguards; failed subdirectory sequences and root end-marker orphans remain raw provenance records and never supply a trusted name. A bounded ordered directory-identity lineage is retained, but no unsampled full path is inferred. It recovers active nonempty root/subdirectory regular files only through exact size-required, image-bounded chains ending at EOC; deleted single-cluster candidates can map directly while multicluster candidates require equivalent complete current-FAT chains and retain the reuse caveat. A bounded full FAT16 allocation scan also inventories unreferenced components relative only to the validated directory sample; use SleuthKit/fsck for exhaustive ownership resolution.
- Native FAT12 analysis validates its sub-4,085 cluster-count class, packed-FAT capacity, and fixed-root geometry before scanning at most 4,096 entries. Every declared packed FAT copy receives the same independent bounds, reserved-entry/media check, and bounded byte comparison; exact first-divergence offsets are retained without choosing a trusted table. It follows active subdirectories only when exact even/odd 12-bit decoding reaches EOC under shared 32-directory/64-cluster/8-MiB limits; incomplete or shared chains cannot supply deleted children. Active directory/file LFNs require intact ordinal/checksum/UTF-16 validation; failed subdirectory sequences and root end-marker orphans remain raw provenance records, and deleted recovery retains its reuse caveat. A bounded ordered directory-identity lineage is retained without claiming an inferred full path. A bounded full FAT12 allocation scan inventories unreferenced components without claiming deletion or filename ownership. Use SleuthKit/fsck for exhaustive recovery.
- Native ext analysis traverses at most 32 allocated active directories under shared 64-block/8-MiB bounds through complete initialized ext4 depth-zero, depth-one, or depth-two extent trees, or ext2/3 direct plus one single-indirect pointer block. Inode, directory-data, extent-tree, indirect-metadata, and data-block reuse is boundedly rejected, and exact intermediate-index/leaf/pointer/data offsets are retained. It recovers at most 128 allocated nonempty regular files from validated root/subdirectory entries when their initialized mapping is complete under 8-MiB/64-block per-file bounds. It does not follow double/triple-indirect blocks or depth-three-and-higher extent trees, journal state, metadata checksums, sparse files, or deleted entries; use fsck/SleuthKit against a copy for exhaustive work.
- Native exFAT analysis independently validates complete main/backup boot regions and compares immutable bytes without choosing an authoritative divergent copy. It traverses the root plus at most 32 active subdirectories under shared 64-cluster/8-MiB bounds, supporting complete NoFatChain extents and exact-EOC FAT chains while rejecting shared clusters and never traversing deleted directories. It validates bounded active allocation-bitmap/upcase metadata; inactive sets require a restored-InUse checksum and name hashes are revalidated only with a trusted full upcase mapping. Root/subdirectory deleted regular files receive initialized-tail zero fill and current bitmap reuse warnings without ownership verdicts. Exhaustive directory enumeration and recovery still require SleuthKit.
- Native TLS certificate inventory reassembles only one bounded (64 KiB) TLS 1.2/1.3 Certificate record per in-order TCP flow and records opaque certificate lengths/fingerprints. It does not decrypt TLS, join multiple TLS records/handshakes, or interpret X.509 subject/issuer/extensions; use tshark or local X.509 tooling for that verification.
- Native HTTP recovery handles complete length-delimited or chunked HTTP/1.x responses, exact inverse-flow request pairing, bounded gzip/deflate content coding, and strictly delimited multipart response parts including Base64 and quoted-printable Content-Transfer-Encoding. It does not support brotli/zstd coding, HTTP/2/3 framing, nested MIME transfer encodings, or arbitrary TCP streams; use tshark for exhaustive protocol reconstruction.
- Native FTP recovery currently accepts observed IPv4 PASV/EPSV or active-mode PORT/EPRT `RETR` downloads and `STOR` uploads after an exact control-channel correlation, including bounded in-order control-line continuation. PASV/EPSV and active-mode `MLSD`/`NLST` listings are preserved as child artifacts, with command-specific `226`/4xx/5xx completion/error provenance. It records exact `AUTH TLS`/`234` provenance and discards later plaintext/stale transfer state, but does not decrypt TLS-protected FTP; use tshark for exhaustive protocol reconstruction.
- Native SMTP recovery accepts bounded retransmission-safe TCP reassembly of DATA/354 control exchanges and DATA body bytes ending in the SMTP dot terminator. It extracts declared flat and `message/rfc822` MIME attachments plus inline Content-ID objects through the standard-library parser, including bounded RFC 2231/5987 decoded names, scans top-level multipart/alternative text parts with MIME provenance, and correlates exact final 250, 251/252 forwarding, and 4xx/5xx replies. It records STARTTLS transitions and suppresses native plaintext parsing after the exact 220 handshake, and recovers complete declared-length BDAT messages with the same bounded MIME attachment handling and final-response provenance. No TLS decryption is attempted.
- Native POP3 recovery accepts only exact TCP/110 `RETR <message-number>` / inverse `+OK` exchanges, then reassembles one bounded dot-terminated multiline response with retransmission-safe packet provenance. Recovered messages receive bounded standard-library MIME attachment handling. It records exact `STLS`/`+OK` provenance and suppresses later plaintext recovery, but does not decrypt TLS or support implicit TLS, UIDL/LIST/TOP, or arbitrary pipelining beyond ordered RETR replies; use tshark for exhaustive protocol reconstruction.
- Native IMAP recovery accepts only full-message `FETCH` requests on TCP/143 whose inverse response supplies one exact `BODY[]`/`RFC822` literal and whose original tag receives a final `OK`. Recovered messages receive bounded standard-library MIME attachment handling. It records exact tagged `STARTTLS`/`OK` transition provenance and suppresses later plaintext recovery, but does not decrypt TLS or support IMAPS, authentication, arbitrary FETCH item syntax, multiple literals, non-message body sections, or general IMAP state reconstruction; use tshark for exhaustive protocol reconstruction.
- Native SMB2 analysis inventories complete bounded TCP/445 Direct TCP NEGOTIATE/TREE_CONNECT/CREATE/CLOSE and SET_INFO rename/delete-disposition exchanges with exact inverse response provenance, retaining dialect/signing/capability/transport limits, validated UNC share paths, relative/target filenames, NTSTATUS, success FileIds, final sizes, attributes, and raw GUID/FILETIME values. It reconstructs only acknowledged WRITE requests or successful READ responses that form a conflict-free stream from offset zero, enforces final EndOfFile when a successful CLOSE is captured, and promotes strictly bounded FileNamesInformation or FileIdBothDirectoryInformation QUERY_DIRECTORY responses as text/JSONL children. NEGOTIATE contexts are bounds-checked but not decoded; SMB3 encryption/compression transform headers are inventoried but their payloads remain opaque. Native support does not parse other directory-information classes, retain partial/gapped transfers as children, apply captured mutations, decrypt SMB3, decompress transforms, or support SMB1; use tshark for exhaustive protocol reconstruction.
- Native PCAP extraction summaries are protocol-scoped; a non-HTTP child never serves as evidence for an HTTP-object finding.
